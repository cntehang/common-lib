# 消息组件使用说明

## 1. 组件概览

`common-lib` 的消息组件基于阿里云 RocketMQ 封装，围绕 `DomainEvent` 提供三类能力：

- `DomainEvent`：普通领域事件，直接发送 MQ，支持集群消费和广播消费。
- `TransactionalDomainEvent`：事务性领域事件，先写入本地 `domain_event_record`，再由定时任务投递 MQ，用于保证本地事务和事件发布最终一致。
- `CommandManager`：基于事务性事件实现的异步命令组件，可异步执行单个命令，也可按顺序执行多个命令。

推荐新项目优先使用 `@EnableTransactionalDomainEvent` + `TransactionalEventPublisher`。只有明确不需要本地事务一致性的场景，才使用 `@EnableDomainEvent` + `EventPublisher` 直接发布。

## 2. 基础配置

### 2.1 Maven/Gradle 依赖

业务服务需要引用包含消息组件的 `common-lib` 版本，并具备以下基础能力：

- Spring Boot。
- Redis：用于普通集群消费者的 24 小时防重和分布式锁。
- 数据库：使用 `@EnableTransactionalDomainEvent` 或 `@EnableCommand` 时需要。
- Scheduling：事务性事件通过定时任务扫描 outbox。
- 阿里云 RocketMQ 配置。

### 2.2 MQ 配置

在业务服务配置文件中增加：

```yaml
aliyun:
  mq:
    accessKey: xxxxx
    accessSecretKey: xxxxx
    nameServer: http://xxxxxx.aliyuncs.com:80
    main:
      topic: tyx-test-master
      groupId: GID-xxx-service-clustering
      broadcastingGroupId: GID-xxx-service-broadcasting
      eventTagPrefix: dev1-
```

字段说明：

- `topic`：RocketMQ topic。
- `groupId`：生产者 groupId，同时作为集群消费 groupId；每个服务应不同。
- `broadcastingGroupId`：广播消费 groupId；使用广播订阅或刷新缓存时必填，且不能与 `groupId` 相同。
- `eventTagPrefix`：事件 tag 前缀。多套环境共用 topic 时，同一环境的服务应配置相同前缀。

最终 MQ tag 为：

```text
eventTagPrefix + event.eventType
```

### 2.3 应用注解配置

普通事件直接发布：

```java
@EnableDomainEvent
@SpringBootApplication
public class Application {
}
```

事务性事件发布：

```java
@EnableTransactionalDomainEvent
@EnableDistributedLock
@EnableScheduling
@EnableAsync
@SpringBootApplication
public class Application {
}
```

命令组件：

```java
@EnableTransactionalDomainEvent
@EnableDistributedLock
@EnableScheduling
@EnableAsync
@EnableCommand(eventType = "XxxServiceCommand")
@SpringBootApplication
public class Application {
}
```

说明：

- `@EnableTransactionalDomainEvent` 用于导入事务性事件发布、outbox 定时投递和消费幂等组件。
- `@EnableDistributedLock` 用于导入事务性投递和普通集群消费所需的分布式锁辅助类。
- `@EnableScheduling` 用于启用 `domain_event_record` 扫描投递任务。
- `@EnableAsync` 用于让事务性事件投递服务的 `@Async` 生效。
- `@EnableCommand` 依赖事务性事件组件；不同服务的 `eventType` 不应相同。

### 2.4 JPA/Repository 扫描

如果项目使用 Spring Data JPA，需要按项目既有方式扫描业务包和 common 包，例如：

```java
@EnableJpaRepositories(basePackageClasses = {Application.class, ThStringUtils.class},
    repositoryBaseClass = ExtendedJpaRepository.class)
@EntityScan(basePackageClasses = {Application.class, ThStringUtils.class})
```

实际类名以业务项目已有配置为准。消息组件自身主要使用 `NamedParameterJdbcTemplate` 操作表，但业务服务需要提供 `DataSource`、事务管理器和 JDBC/JPA 基础配置。

## 3. DomainEvent 普通事件

### 3.1 定义事件

所有事件参数继承 `DomainEvent`：

```java
public class FlightBookingCompletedEvent extends DomainEvent {

  private String orderId;

  public FlightBookingCompletedEvent() {
  }

  public FlightBookingCompletedEvent(String orderId) {
    super("FlightBookingCompleted");
    this.orderId = orderId;
    setKey(orderId);
  }
}
```

约定：

- `eventType` 必须稳定、唯一，和 MQ tag 的业务部分一致。
- `key` 是业务标识，会作为 MQ message key。
- 事件类需要保留无参构造函数，便于消费者反序列化。
- 事件名建议使用过去式，例如 `OrderPaidEvent`、`FlightBookingCompletedEvent`。

### 3.2 直接发布事件

```java
@Service
@AllArgsConstructor
public class FlightService {

  private final EventPublisher eventPublisher;

  public void completeBooking(String orderId) {
    eventPublisher.publish(new FlightBookingCompletedEvent(orderId));
  }
}
```

直接发布特点：

- 调用时立即发送 MQ。
- 发送失败会按 1 秒、3 秒、10 秒重试，最终失败时抛异常。
- 不经过本地 outbox 表，不保证和业务数据库事务最终一致。

### 3.3 延迟发布

```java
eventPublisher.publish(event, System.currentTimeMillis() + 3000);
```

`startDeliverTime` 为绝对毫秒时间，最大延迟时间受 RocketMQ 限制。

## 4. 事件订阅

### 4.1 集群消费

集群消费中，同一个 group 下，一条消息只会被一个实例处理。

```java
@Service
public class FlightBookingCompletedSubscriber implements ClusteringEventSubscriber {

  @Override
  public String subscribedEventType() {
    return "FlightBookingCompleted";
  }

  @Override
  public Class<? extends DomainEvent> getEventClass() {
    return FlightBookingCompletedEvent.class;
  }

  @Override
  public void handleEvent(DomainEvent event) {
    FlightBookingCompletedEvent actual = (FlightBookingCompletedEvent) event;
    // 处理业务逻辑
  }
}
```

注意：

- 当前 `ClusteringMqConsumer` 约定同一个 `eventType` 在同一服务内只能有一个集群订阅者。
- 普通集群订阅者会使用 Redis 24 小时防重。
- 普通集群订阅者会使用分布式锁，锁粒度为 `eventType + eventKey`。
- 消费失败时返回 `ReconsumeLater`，由 MQ 后续重试。

### 4.2 广播消费

广播消费中，同一条消息会被每个服务实例处理，适合本地缓存刷新等场景。

```java
@Service
public class LocalCacheRefreshSubscriber implements BroadcastingEventSubscriber {

  @Override
  public String subscribedEventType() {
    return "FlightBookingCompleted";
  }

  @Override
  public Class<? extends DomainEvent> getEventClass() {
    return FlightBookingCompletedEvent.class;
  }

  @Override
  public void handleEvent(DomainEvent event) {
    // 刷新本机缓存
  }
}
```

广播消费要求配置 `broadcastingGroupId`。同一 `eventType` 可以有多个广播订阅者。

## 5. TransactionalDomainEvent 事务性事件

### 5.1 使用场景

当业务数据库变更和事件发布必须保持最终一致时，使用 `TransactionalEventPublisher`：

- 创建订单后发布订单创建事件。
- 支付成功后发布支付成功事件。
- 业务状态变更后触发下游异步处理。

事务性发布不是直接发送 MQ，而是在业务事务内写入 `domain_event_record`，再由定时任务异步发送。

### 5.2 建表

使用 `@EnableTransactionalDomainEvent` 的服务需要创建：

```sql
create table if not exists `domain_event_record`
(
  `id`                 varchar(50)  not null comment 'PK, uuid',
  `event_key`          varchar(100) not null comment '事件key',
  `event_type`         varchar(100) not null comment '事件类型',
  `topic`              varchar(30)  null     comment '事件对应的mq的topic',
  `publisher`          varchar(200) null     comment '事件发布者',
  `start_deliver_time` varchar(23)  null     comment '设置消息的延时投递时间',
  `trace_id`           varchar(200) null     comment '发布事件所在的TraceId',
  `body`               text         null     comment '事件发送的消息body',
  `status`             varchar(30)  not null comment '事件的发送状态',
  `publish_time`       varchar(23)  null     comment '事件发布时间',
  `count`              int(11)      not null comment '实际发送的次数，初始为0',
  `create_time`        varchar(23)  not null comment '创建时间',
  `update_time`        varchar(23)  not null comment '更新时间',
  primary key (`id`),
  unique key `uk_domain_event_record_type_key` (`event_type`, `event_key`),
  key `idx_domain_event_record_status` (`status`),
  key `idx_domain_event_record_status_create_time` (`status`, `create_time`)
) engine = innodb default charset = utf8mb4 comment = '领域事件记录表';
```

### 5.3 发布事务性事件

```java
@Service
@AllArgsConstructor
public class FlightOrderService {

  private final TransactionalEventPublisher transactionalEventPublisher;

  @Transactional
  public void completeBooking(String orderId) {
    // 更新业务表
    transactionalEventPublisher.publish(new FlightBookingCompletedEvent(orderId));
  }
}
```

`publish(...)` 特点：

- 写入 `domain_event_record`。
- 业务事务提交后，定时任务每 2 秒扫描 `WaitSend` 记录并发送 MQ。
- 发送成功后状态更新为 `SendSuccess`。
- 发送失败会累加 `count`，超过 5 次后更新为 `SendFailed`。

### 5.4 发布去重

如果同一业务动作可能被多个入口重复触发，且同一事件类型、同一业务对象只应发布一次，使用 `publishOnce`：

```java
boolean published = transactionalEventPublisher.publishOnce(
    new FlightBookingCompletedEvent(orderId),
    "FlightBookingCompleted:" + orderId
);
```

要求：

- `idempotentKey` 非空，长度不超过 100。
- `idempotentKey` 必须稳定，不能使用随机值或时间戳。
- 首次插入返回 `true`。
- 重复插入返回 `false`，不会再次写 outbox，也不会再次投递 MQ。

普通事件不要为了统一写法而全部改成 `publishOnce`。

### 5.5 直接发布

`TransactionalEventPublisher` 也提供：

```java
transactionalEventPublisher.publishDirectly(event);
```

该方法等价于 `EventPublisher.publish(...)`，不经过 outbox 表。仅在明确不需要事务一致性且对性能有要求时使用。

## 6. 消费幂等

### 6.1 普通消费者幂等

普通 `ClusteringEventSubscriber` 使用 Redis 做 24 小时防重：

```text
MQ_Consumer_Idempotent_${eventType}_${eventKey}
```

并使用分布式锁避免并发重复执行：

```text
MQ_Consumer_Lock_${eventType}_${eventKey}
```

这是轻量保护，不作为永久幂等依据。

### 6.2 数据库消费幂等

关键订阅者可以实现 `DatabaseIdempotentClusteringEventSubscriber`：

```java
@Service
public class FlightBookingCompletedSubscriber implements DatabaseIdempotentClusteringEventSubscriber {

  @Override
  public String subscriberId() {
    return "flight-service.flight-booking-completed";
  }

  @Override
  public String subscribedEventType() {
    return "FlightBookingCompleted";
  }

  @Override
  public Class<? extends DomainEvent> getEventClass() {
    return FlightBookingCompletedEvent.class;
  }

  @Override
  public void handleEvent(DomainEvent event) {
    // 关键业务处理
  }
}
```

数据库幂等订阅者特点：

- 不使用 Redis 防重。
- 不获取消费分布式锁。
- 在一个事务中完成消费记录占位、业务处理、成功状态更新。
- 同一 `event_key + event_type + subscriber_id` 只成功处理一次。
- `handleEvent` 抛异常时事务回滚，不写成功记录，MQ 后续可重试。

需要创建消费记录表：

```sql
create table if not exists `domain_event_consume_record`
(
  `id`             varchar(50)  not null comment 'PK, uuid',
  `event_key`      varchar(100) not null comment '事件key',
  `event_type`     varchar(100) not null comment '事件类型',
  `subscriber_id`  varchar(200) not null comment '订阅者稳定标识',
  `status`         varchar(30)  not null comment '消费状态',
  `consume_time`   varchar(23)  null     comment '消费成功时间',
  `error_message`  varchar(500) null     comment '错误信息，预留字段',
  `create_time`    varchar(23)  not null comment '创建时间',
  `update_time`    varchar(23)  not null comment '更新时间',
  primary key (`id`),
  unique key `uk_event_consume` (`event_key`, `event_type`, `subscriber_id`),
  key `idx_domain_event_consume_record_event` (`event_type`, `event_key`),
  key `idx_domain_event_consume_record_subscriber` (`subscriber_id`)
) engine = innodb default charset = utf8mb4 comment = '领域事件消费记录表';
```

注意：

- `subscriberId()` 一旦上线，应视为持久化协议。
- 不要使用类实例地址、机器名、pod 名称或随机值。
- 如果 `handleEvent` 内有外部调用，外部系统仍需按业务 key 幂等，或拆为后续任务/事件。

## 7. CommandManager 异步命令

### 7.1 使用场景

`CommandManager` 用于把业务动作封装成异步命令：

- 当前流程不需要同步等待结果。
- 希望使用 MQ 重试执行异步任务。
- 多个异步步骤需要按顺序执行，且失败后能从失败步骤继续。

命令组件依赖事务性事件组件，因此必须先启用 `@EnableTransactionalDomainEvent`。

### 7.2 建表

使用 `@EnableCommand` 时需要创建：

```sql
create table if not exists `command_record`
(
  `id`                   varchar(50)  not null comment 'PK, uuid',
  `event_key`            varchar(100) not null comment '事件key',
  `command_type`         varchar(100) not null comment '命令类型',
  `command_args`         text         null     comment '命令参数对象的json表示',
  `command_return_value` text         null     comment '命令返回对象的json表示',
  `success`              bit(1)       not null comment '是否已执行成功',
  `seq_no`               int(11)      not null comment '命令的顺序号，从1开始',
  `create_time`          varchar(23)  not null comment '创建时间',
  `update_time`          varchar(23)  not null comment '更新时间',
  primary key (`id`),
  key `idx_command_record_event_key` (`event_key`)
) engine = innodb default charset = utf8mb4 comment = '命令记录表';

create table if not exists `command_record_his`
(
  `id`            varchar(50)  not null comment 'PK, uuid',
  `command_id`    varchar(50)  not null comment '命令id',
  `success`       bit(1)       not null comment '执行是否成功',
  `error_message` varchar(300) null     comment '执行失败时的错误消息',
  `create_time`   varchar(23)  not null comment '创建时间',
  primary key (`id`),
  key `idx_command_record_his_command_id` (`command_id`)
) engine = innodb default charset = utf8mb4 comment = '命令执行历史表';
```

### 7.3 定义命令

```java
@Service
public class CreateFlightBillCommand implements Command<CreateFlightBillArgs, CreateFlightBillResult> {

  @Override
  public String getCommandType() {
    return "CreateFlightBill";
  }

  @Override
  public CreateFlightBillResult run(CreateFlightBillArgs args) {
    // 执行业务逻辑
    return new CreateFlightBillResult(args.getOrderId());
  }
}
```

要求：

- `Command<T, R>` 的泛型类型必须明确，组件会通过泛型解析参数和返回值类型。
- `getCommandType()` 在同一服务内必须唯一。
- 参数和返回值需要能被 JSON 序列化/反序列化。

### 7.4 投递单个命令

```java
commandManager.queueCommand("CreateFlightBill", new CreateFlightBillArgs(orderId));
```

执行流程：

```text
queueCommand
  -> 创建 CommandEvent
  -> TransactionalEventPublisher 写入 domain_event_record
  -> 定时任务投递 MQ
  -> CommandEventSubscriber 接收事件
  -> CommandLocator 根据 commandType 查找 Command bean
  -> 反序列化 args
  -> command.run(args)
```

单个命令不会写 `command_record`，失败后依赖 MQ 对同一命令事件重试。

### 7.5 投递多个顺序命令

```java
commandManager.queueCommands(
    CommandInfo.of("CreateFlightBill", new CreateFlightBillArgs(orderId)),
    CommandInfo.of("NotifyFlightBillCreated", new NotifyArgs(orderId))
);
```

执行流程：

```text
queueCommands
  -> 生成聚合 CommandEvent
  -> 多条子命令写入 command_record，seq_no 从 1 开始
  -> TransactionalEventPublisher 写入 domain_event_record
  -> CommandEventSubscriber 按 seq_no 执行子命令
  -> 每个子命令成功后更新 success = true 和 command_return_value
  -> 某个子命令失败时记录 command_record_his，并抛异常等待 MQ 重试
```

重试时，已成功的前序命令不会重复执行。组件会读取前序命令的 `command_return_value`，并通过 `CommandExecuteContext.getPreCommandReturnValue()` 传递给后续命令：

```java
Object preResult = CommandExecuteContext.getPreCommandReturnValue();
```

### 7.6 命令组件注意事项

- 命令事件的 `@EnableCommand(eventType = "...")` 在不同服务中必须不同。
- 命令执行应尽量幂等，因为 MQ 可能重复投递。
- 多命令场景只保证已成功子命令不会再次执行，不保证外部系统 exactly-once。
- 命令失败历史只记录失败，不会自动告警；业务服务应结合日志和表数据监控失败情况。

## 8. 新项目推荐接入方式

### 8.1 只需要普通 MQ 事件

配置：

```java
@EnableDomainEvent
@EnableDistributedLock
@SpringBootApplication
public class Application {
}
```

适用：

- 不要求事件发布和本地事务最终一致。
- 可接受直接发送 MQ 失败时抛异常。

### 8.2 推荐默认方式：事务性事件

配置：

```java
@EnableTransactionalDomainEvent
@EnableDistributedLock
@EnableScheduling
@EnableAsync
@SpringBootApplication
public class Application {
}
```

需要：

- MQ 配置。
- Redis 配置。
- 数据库配置。
- `domain_event_record` 表。

### 8.3 事务性事件 + 消费数据库幂等

在 8.2 基础上：

- 创建 `domain_event_consume_record`。
- 关键订阅者实现 `DatabaseIdempotentClusteringEventSubscriber`。
- 显式覆盖稳定 `subscriberId()`。

### 8.4 事务性事件 + 命令组件

在 8.2 基础上：

```java
@EnableCommand(eventType = "XxxServiceCommand")
```

需要额外创建：

- `command_record`
- `command_record_his`

## 9. 运维与排查

常用 SQL：

```sql
-- 查询待发送事件
select *
from domain_event_record
where status = 'WaitSend'
order by create_time;

-- 查询发送失败事件
select *
from domain_event_record
where status = 'SendFailed'
order by update_time desc;

-- 查询某个事件的消费记录
select *
from domain_event_consume_record
where event_type = '<event_type>'
  and event_key = '<event_key>';

-- 查询未完成命令
select *
from command_record
where success = false
order by create_time;

-- 查询命令失败历史
select *
from command_record_his
order by create_time desc;
```

常见问题：

- 消息没有发送：检查 `@EnableScheduling`、`domain_event_record.status`、MQ 配置和 `SendFailed` 记录。
- 消费者没有启动：检查服务内是否存在订阅者、MQ groupId、topic、tag 前缀。
- 广播消费者启动失败：检查 `broadcastingGroupId` 是否配置。
- 数据库幂等订阅者消费失败：检查是否使用 `@EnableTransactionalDomainEvent`，以及 `domain_event_consume_record` 是否存在。
- 命令找不到：检查 `Command` bean 是否被 Spring 扫描，`getCommandType()` 是否和投递时一致。

## 10. 设计边界

- 组件不承诺严格 exactly-once。
- 事务性事件保证的是本地事务和 MQ 发布的最终一致，不保证消费者业务一定成功。
- 普通 Redis 防重是 24 小时快速保护，不是永久幂等依据。
- 数据库消费幂等只保护本地事务内的业务处理，外部系统调用仍需业务自行保证幂等。
- `publishDirectly` 不经过 outbox，不支持发布去重。
