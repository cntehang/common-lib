# 通用事件发布去重与消费幂等方案迁移指南

## 1. 适用范围

本文面向已经使用事务性事件组件的业务服务，即应用启动类已经引用 `@EnableTransactionalDomainEvent` 的服务。

如果服务只使用 `@EnableDomainEvent`，本指南中的 `domain_event_record` 唯一约束迁移不适用；如果服务没有显式实现 `DatabaseIdempotentClusteringEventSubscriber`，也不需要创建 `domain_event_consume_record`。

本次迁移包含两类能力：

- Outbox 发布去重：新增 `TransactionalEventPublisher.publishOnce(...)`，并要求 `domain_event_record` 增加 `(event_type, event_key)` 唯一约束。
- Inbox 消费幂等：仅对显式实现 `DatabaseIdempotentClusteringEventSubscriber` 的关键订阅者启用，使用 `domain_event_consume_record` 保证同一事件、同一订阅者只成功处理一次。

普通 `publish(...)` 和普通 `ClusteringEventSubscriber` 保持兼容，不需要为了升级而全部改造。

## 2. 迁移前检查

### 2.1 确认服务接入方式

检查应用启动类或配置类：

```bash
grep -R "EnableTransactionalDomainEvent\|EnableDomainEvent" -n src/main/java
```

确认结果：

- 已使用 `@EnableTransactionalDomainEvent`：需要执行 `domain_event_record` 唯一约束检查和迁移。
- 仅使用 `@EnableDomainEvent`：不需要 outbox 表迁移；只有将来改用事务性发布时才需要。
- 同时存在集群消费者：继续检查是否有关键订阅者需要接入数据库消费幂等。

### 2.2 检查 `domain_event_record` 历史重复数据

上线唯一约束前必须检查历史数据：

```sql
select event_type, event_key, count(*) as cnt
from domain_event_record
group by event_type, event_key
having count(*) > 1;
```

处理原则：

- 查询为空：可以增加唯一约束。
- 查询不为空：先确认重复记录是否属于历史重复发布，再决定归档、清理或暂缓迁移。
- 不要直接删除重复记录，尤其是 `WaitSend`、`SendFailed` 或仍在排查中的记录。

建议同时检查待发送重复记录，避免上线后定时任务继续发送历史重复消息：

```sql
select event_type, event_key, status, count(*) as cnt
from domain_event_record
where status in ('WaitSend', 'SendFailed')
group by event_type, event_key, status
having count(*) > 1;
```

### 2.3 检查唯一约束是否已存在

```sql
show index from domain_event_record
where key_name = 'uk_domain_event_record_type_key';
```

如果已经存在，不需要重复执行 DDL。

### 2.4 梳理需要发布去重的事件

搜索事务性发布点：

```bash
grep -R "transactionalEventPublisher.publish" -n src/main/java
```

逐个判断：

- 普通业务事件：继续使用 `publish(...)`。
- 可能被多个入口重复触发、且业务语义要求同一业务对象只发布一次的事件：改为 `publishOnce(...)`。
- 已手动设置固定 `event.key` 后仍调用 `publish(...)` 的代码：需要重点检查，新增唯一约束后重复写入会失败；建议改为 `publishOnce(...)` 或重新确认 key 语义。

`publishOnce` 的 `idempotentKey` 必须稳定、可读、长度不超过 100，例如：

```java
"TMC-FlightBookingCompleted:" + orderId
```

### 2.5 梳理需要消费幂等的订阅者

搜索集群订阅者：

```bash
grep -R "implements .*ClusteringEventSubscriber" -n src/main/java
```

建议只有满足以下条件的订阅者才接入数据库消费幂等：

- 重复消费会导致重复记账、重复生成明细、重复扣减、重复发布关键后续事件等业务副作用。
- 服务本身具备数据库事务能力，并能创建 `domain_event_consume_record`。
- 订阅者内部主要操作本地数据库，或外部调用已经具备业务幂等。

以下订阅者通常不需要接入：

- 缓存刷新、通知、日志、指标等允许短期重复的轻量订阅者。
- 没有数据库的服务。
- 只依赖 Redis 24 小时快速防重即可接受风险的普通订阅者。

### 2.6 检查外部副作用

如果准备让订阅者实现 `DatabaseIdempotentClusteringEventSubscriber`，必须检查 `handleEvent` 内是否存在耗时外部调用，例如 HTTP、RPC、第三方系统、文件上传、外部 MQ。

注意：

- 数据库消费幂等会把消费记录占位、业务处理、成功记录更新放进同一个事务。
- 如果事务中包含耗时外部调用，会扩大事务范围，增加锁等待和连接占用。
- 外部调用成功但本地事务回滚时，MQ 重试仍会再次执行订阅者，因此外部系统也需要幂等。

推荐做法：

- 优先让外部系统按业务 key 幂等。
- 或将外部副作用拆成后续事件、任务表、补偿任务，由独立流程处理。

## 3. 数据库迁移

### 3.1 增加 outbox 唯一约束

在确认 `domain_event_record` 无重复数据后执行：

```sql
alter table domain_event_record
  add unique key uk_domain_event_record_type_key (event_type, event_key);
```

执行后验证：

```sql
show index from domain_event_record
where key_name = 'uk_domain_event_record_type_key';
```

### 3.2 按需创建 inbox 消费记录表

只有服务内存在 `DatabaseIdempotentClusteringEventSubscriber` 时才需要创建：

```sql
create table if not exists `domain_event_consume_record`
(
  `id`             varchar(50)  not null comment 'PK, uuid',
  `event_key`      varchar(100) not null comment '事件key',
  `event_type`     varchar(100) not null comment '事件类型',
  `subscriber_id`  varchar(200) not null comment '订阅者稳定标识',
  `status`         varchar(30)  not null comment '消费状态',
  `consume_time`   varchar(23)  null     comment '消费成功时间',
  `error_message`  varchar(500) null     comment '错误信息，预留字段',
  `create_time`    varchar(23)  not null comment '创建时间',
  `update_time`    varchar(23)  not null comment '更新时间',
  primary key (`id`),
  unique key `uk_event_consume` (`event_key`, `event_type`, `subscriber_id`),
  key `idx_domain_event_consume_record_event` (`event_type`, `event_key`),
  key `idx_domain_event_consume_record_subscriber` (`subscriber_id`)
) engine = innodb default charset = utf8mb4 comment = '领域事件消费记录表';
```

执行后验证：

```sql
show tables like 'domain_event_consume_record';
show index from domain_event_consume_record
where key_name = 'uk_event_consume';
```

## 4. 代码迁移步骤

### 4.1 升级 `common-lib`

将业务服务依赖升级到包含本方案的 `common-lib` 版本。

升级后，已使用 `@EnableTransactionalDomainEvent` 的服务会自动导入消费幂等相关组件，但不会自动让所有订阅者进入数据库幂等路径。

### 4.2 改造需要发布去重的事件

将需要业务级发布去重的发布点从：

```java
transactionalEventPublisher.publish(event);
```

改为：

```java
transactionalEventPublisher.publishOnce(event, idempotentKey);
```

要求：

- `idempotentKey` 必须由业务稳定字段组成。
- 同一事件类型下，同一业务对象应生成同一个 key。
- 不要使用随机 UUID、时间戳、机器名、实例 id。
- 普通事件不要为了统一写法而改成 `publishOnce`。

### 4.3 改造需要数据库消费幂等的订阅者

将关键订阅者从：

```java
public class XxxSubscriber implements ClusteringEventSubscriber {
}
```

改为：

```java
public class XxxSubscriber implements DatabaseIdempotentClusteringEventSubscriber {

  @Override
  public String subscriberId() {
    return "service-name.xxx-subscriber";
  }
}
```

要求：

- `subscriberId()` 必须稳定，一旦上线应视为持久化协议。
- 不要使用 `getInstanceId()`、pod 名、IP、机器名、随机值。
- 类重命名、包路径调整、订阅者拆分时，需要评估是否继续沿用旧 `subscriberId`。
- 如果没有创建 `domain_event_consume_record`，该订阅者消费时会失败并触发 MQ 重试，不能静默降级。

### 4.4 普通订阅者兼容说明

普通 `ClusteringEventSubscriber` 仍使用 Redis 24 小时防重和分布式锁。

本版本会将普通订阅者的 Redis 防重 key 和分布式锁 key 粒度从仅 `eventKey` 调整为 `eventType + eventKey`，用于避免不同事件类型复用相同业务 key 时互相误判。

迁移影响：

- 新版本不会读取旧版本仅按 `eventKey` 写入的 Redis `OK` key。
- 正常情况下 MQ 已提交的消息不会再次投递，因此影响很小。
- 如果升级窗口内存在 MQ 重试、积压或人工重放，普通订阅者仍需确认重复消费风险。
- 不能接受重复消费风险的关键订阅者，应接入 `DatabaseIdempotentClusteringEventSubscriber`。

## 5. 验证步骤

### 5.1 启动验证

启动服务后检查：

- 应用能正常启动。
- `ClusteringMqConsumer` 正常订阅 tag。
- 没有 `Database idempotent event subscriber requires EnableTransactionalDomainEvent` 类似错误。
- 没有 `domain_event_record` 或 `domain_event_consume_record` 表不存在错误。

### 5.2 发布去重验证

对已改为 `publishOnce` 的事件，触发两次相同业务操作，验证：

```sql
select event_type, event_key, count(*) as cnt
from domain_event_record
where event_type = '<event_type>'
  and event_key = '<idempotent_key>'
group by event_type, event_key;
```

预期：

- 只存在一条记录。
- 第二次发布返回 `false` 或日志出现重复发布跳过的 `warn`。
- MQ 不会因为第二次重复发布而新增投递。

同时验证普通 `publish(...)`：

- 未改造的普通事件仍能正常写入 `domain_event_record`。
- 普通事件默认 UUID key，不应触发唯一约束冲突。

### 5.3 数据库消费幂等验证

对已实现 `DatabaseIdempotentClusteringEventSubscriber` 的订阅者，首次成功消费后检查：

```sql
select event_key, event_type, subscriber_id, status, consume_time
from domain_event_consume_record
where event_key = '<event_key>'
  and event_type = '<event_type>'
  and subscriber_id = '<subscriber_id>';
```

预期：

- 存在一条记录。
- `status = 'Success'`。
- `consume_time` 不为空。

重复投递同一消息后验证：

- 业务副作用没有重复产生。
- `domain_event_consume_record` 仍只有一条记录。
- 日志出现重复消费跳过的 `warn`。

异常重试验证：

- 人为让 `handleEvent` 抛出异常。
- 消费记录不应提交为 `Success`。
- MQ 返回重试后，再次恢复处理逻辑应能重新消费成功。

### 5.4 普通订阅者验证

对未接入数据库幂等的普通订阅者验证：

- 消费成功后仍写 Redis `OK`。
- 分布式锁和 Redis 防重 key 使用 `eventType + eventKey` 粒度。
- 不会写入 `domain_event_consume_record`。

## 6. 上线顺序建议

推荐按服务逐个迁移：

1. 盘点服务中是否使用 `@EnableTransactionalDomainEvent`。
2. 执行 `domain_event_record` 重复数据检查。
3. 清理或确认历史重复数据。
4. 添加 `uk_domain_event_record_type_key` 唯一约束。
5. 升级 `common-lib`。
6. 只将明确需要发布去重的事件改为 `publishOnce`。
7. 只将关键消费者改为 `DatabaseIdempotentClusteringEventSubscriber`。
8. 如存在数据库幂等订阅者，创建 `domain_event_consume_record`。
9. 灰度发布并观察日志、MQ 重试、outbox 记录和消费记录。
10. 全量发布。

如果服务暂时只升级 `common-lib`，不改任何发布点和订阅者：

- 仍需要先处理 `domain_event_record` 唯一约束迁移。
- 不需要创建 `domain_event_consume_record`。
- 普通消费者会受到 Redis/锁 key 粒度升级影响，需关注升级窗口内的 MQ 重试消息。

## 7. 回滚策略

### 7.1 代码回滚

- `publishOnce(...)` 发布点可回滚为 `publish(...)`。
- 数据库幂等订阅者可移除 `DatabaseIdempotentClusteringEventSubscriber`，恢复普通消费路径。
- 回滚前确认是否存在依赖数据库幂等保护的重复消息风险。

### 7.2 数据库回滚

`domain_event_consume_record` 可保留，不影响普通消费路径。

如必须回滚 outbox 唯一约束：

```sql
alter table domain_event_record
  drop index uk_domain_event_record_type_key;
```

回滚前需要确认：

- 没有业务依赖该唯一约束保证发布去重。
- 回滚后重复发布风险可接受，或业务侧已有其他保护。

## 8. 常见问题

### 8.1 所有使用 `@EnableTransactionalDomainEvent` 的服务都要建消费记录表吗？

不需要。只有存在 `DatabaseIdempotentClusteringEventSubscriber` 的服务才需要 `domain_event_consume_record`。

### 8.2 所有发布都要改成 `publishOnce` 吗？

不需要。只有业务语义要求“同一事件类型 + 同一业务 key 只发布一次”的事件才改为 `publishOnce`。

### 8.3 数据库幂等订阅者还需要 Redis 防重吗？

不需要。数据库幂等订阅者只使用 `domain_event_consume_record`，不再叠加 Redis 防重和分布式锁。

### 8.4 `subscriberId` 可以用类名默认值吗？

可以，但关键业务订阅者更建议显式覆盖。类名和包路径后续可能调整，显式业务 id 更稳定。

### 8.5 事务中有外部调用怎么办？

优先让外部调用按业务 key 幂等，或拆成后续事件/任务。不要依赖本地数据库消费记录去保证外部系统 exactly-once。
