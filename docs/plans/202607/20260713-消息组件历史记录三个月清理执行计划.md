# 消息组件历史记录三个月清理执行计划

## 1. 背景与目标

`common-lib` 消息组件使用以下表保存事件发布、消费幂等和聚合命令执行记录：

- `domain_event_record`：事务性事件 Outbox 记录。
- `domain_event_consume_record`：数据库幂等消费记录。
- `command_record`：聚合命令的子命令和执行检查点。
- `command_record_his`：命令执行失败历史。

随着记录持续增长，表和索引体积会增加，影响数据写入、唯一索引检查、备份恢复和运维查询效率。业务已确认上述数据只需保留最近三个月。

本计划的目标是：

1. 在 `common-lib` 中增加统一的消息记录清理能力。
2. 每日定时、分批删除超过三个月的可清理记录。
3. 避免大事务、长时间锁表、过量 Undo/Redo 和主从复制延迟。
4. 保留待发送事件和异常消费记录；超过三个月的命令按业务约定直接废弃。
5. 让各业务服务显式决定是否启用及需要清理的表，不在升级 `common-lib` 后默认删除数据。

本计划只描述执行步骤，计划评审通过后再开始代码实现和生产数据清理。

## 2. 执行原则

### 2.1 统一保留时间

- 保留时间默认为 3 个月。
- 截止时间使用 `BjTime.now().minusMonths(3)` 计算。
- 数据库字段当前为 `yyyy-MM-dd HH:mm:ss.SSS` 字符串，清理 SQL 继续使用相同格式比较。

### 2.2 只自动清理终态数据

| 表 | 自动清理条件 | 不自动清理的数据 |
| --- | --- | --- |
| `domain_event_record` | `status in ('SendSuccess', 'SendFailed')` 且 `create_time` 早于截止时间 | `WaitSend` |
| `domain_event_consume_record` | `status = 'Success'` 且 `create_time` 早于截止时间 | `Processing` 或其他异常状态 |
| `command_record_his` | `create_time` 早于截止时间 | 无 |
| `command_record` | 同一 `event_key` 下的整组记录均早于截止时间，不判断 `success` | 无 |

`WaitSend` 和 `Processing` 超过三个月时，本阶段只记录告警，不直接删除。命令记录的三个月保留期同时是命令执行有效期，超期后无论成功或失败都不再恢复执行。

### 2.3 分批和小事务

- 每批默认删除 1000 条。
- 每一批独立提交，不把整次任务放在一个大事务中。
- 单次任务每张表默认最多执行 50 批，即最多清理 50000 条。
- 首次存量清理可先将批次大小调整为 500，根据数据库负载再逐步提高。

### 2.4 多实例互斥

使用现有 `DistributedLockHelper` 获取固定分布式锁：

```text
MessageRecordCleanupTask
```

锁过期时间建议设置为 30 分钟，防止多实例同时执行清理。如单次任务可能超过 30 分钟，应优先降低单次最大批次数，而不是无限延长锁时间。

## 3. `common-lib` 代码改动范围

### 3.1 新增清理配置

新增 `MessageRecordCleanupProperties`，建议配置前缀为：

```text
tehang.message.cleanup
```

属性定义：

| 属性 | 默认值 | 说明 |
| --- | --- | --- |
| `enabled` | `false` | 总开关，默认不启用 |
| `retentionMonths` | `3` | 保留月数 |
| `batchSize` | `1000` | 每批数量 |
| `maxBatchesPerRun` | `50` | 单次任务每张表最大批次数 |
| `cron` | `0 30 3 * * ?` | 每日 03:30 执行 |
| `eventRecordEnabled` | `true` | 是否清理事件记录 |
| `consumeRecordEnabled` | `false` | 是否清理消费记录 |
| `commandRecordEnabled` | `false` | 是否清理命令记录及历史 |

`consumeRecordEnabled` 和 `commandRecordEnabled` 默认为 `false`，避免业务库没有创建对应表时任务执行失败。

业务服务配置示例：

```yaml
tehang:
  message:
    cleanup:
      enabled: true
      retentionMonths: 3
      batchSize: 1000
      maxBatchesPerRun: 50
      cron: "0 30 3 * * ?"
      eventRecordEnabled: true
      consumeRecordEnabled: true
      commandRecordEnabled: true
```

### 3.2 新增清理任务

新增 `MessageRecordCleanupTask`：

- 使用 `@Scheduled` 每日触发。
- 时区固定为 `Asia/Shanghai`。
- 当 `enabled = false` 时不创建清理 Bean，优先使用 `@ConditionalOnProperty`控制。
- 获取分布式锁后调用 `MessageRecordCleanupService`。
- 任务开始和结束记录 `INFO` 日志，包含截止时间、各表删除数量和总耗时。
- 单表清理失败时记录 `ERROR`，本次任务停止，不吞掉异常细节。

### 3.3 新增清理服务

新增 `MessageRecordCleanupService`，职责仅包括：

1. 根据配置计算三个月前的截止时间。
2. 按固定顺序调用清理仓储。
3. 控制每张表的最大批次数。
4. 汇总并返回各表删除数量。
5. 在删除前统计超过三个月的 `WaitSend` 和 `Processing` 记录数，存在时记录 `WARN`。

服务不负责拼接 SQL，也不直接依赖 MQ 生产者或消费者，避免清理逻辑侵入消息主流程。

### 3.4 新增清理仓储

新增 `MessageRecordCleanupJdbcRepository`，集中封装清理专用 SQL：

- `deleteEventRecordsBefore(BjTime cutoffTime, int batchSize)`。
- `deleteConsumeRecordsBefore(BjTime cutoffTime, int batchSize)`。
- `deleteCommandHistoryBefore(BjTime cutoffTime, int batchSize)`。
- `findExpiredCommandEventKeysBefore(BjTime cutoffTime, int eventBatchSize)`。
- `deleteCommandHistoryByEventKeys(List<String> eventKeys)`。
- `deleteCommandRecordsByEventKeys(List<String> eventKeys)`。
- 超期 `WaitSend` 和 `Processing` 记录统计方法。

所有查询和删除都使用命名参数，不使用 `String.format` 拼接时间、状态、批次数或 `event_key`。

### 3.5 启用方式

建议在 `EnableTransactionalDomainEvent` 中导入清理配置类，并使用 `@ConditionalOnProperty` 保证只有显式配置 `tehang.message.cleanup.enabled=true` 时才创建任务、服务和仓储。

`@EnableCommand` 依赖 `@EnableTransactionalDomainEvent`，因此不需要再定义第二套定时任务。是否访问命令表由 `commandRecordEnabled` 控制。

## 4. 清理 SQL 设计

### 4.1 事件记录

```sql
delete from domain_event_record
where status in ('SendSuccess', 'SendFailed')
  and create_time < :cutoff_time
order by create_time
limit :batch_size;
```

不得删除 `WaitSend` 记录。

### 4.2 消费记录

```sql
delete from domain_event_consume_record
where status = 'Success'
  and create_time < :cutoff_time
order by create_time
limit :batch_size;
```

如表中存在超期 `Processing` 记录，只记录告警并由人工检查事务配置或历史异常数据。

### 4.3 命令历史

```sql
delete from command_record_his
where create_time < :cutoff_time
order by create_time
limit :batch_size;
```

命令历史先于命令主记录删除，以兼容业务库可能自行增加的外键约束。

### 4.4 命令记录

命令记录必须按 `event_key` 整组删除，不得只删除聚合命令中的部分子命令。

先查询可清理的 `event_key`：

```sql
select distinct expired.event_key
from command_record expired
where expired.create_time < :cutoff_time
  and not exists (
    select 1
    from command_record retained
    where retained.event_key = expired.event_key
      and retained.create_time >= :cutoff_time
  )
order by expired.event_key
limit :event_batch_size;
```

在同一小事务中先删除对应命令历史，再删除命令组：

```sql
delete his
from command_record_his his
inner join command_record command on command.id = his.command_id
where command.event_key in (:event_keys);
```

```sql
delete from command_record
where event_key in (:event_keys);
```

清理条件不判断 `success`。一旦超过三个月，未完成命令也按业务规则直接废弃。

## 5. 数据库索引调整

### 5.1 事件表

`domain_event_record` 已有 `(status, create_time)` 索引，不需要重复创建。上线前通过以下 SQL 确认：

```sql
show index from domain_event_record;
```

### 5.2 其他表

根据清理条件增加：

```sql
alter table domain_event_consume_record
  add index idx_consume_status_create_time (status, create_time);

alter table command_record
  add index idx_command_create_event (create_time, event_key);

alter table command_record_his
  add index idx_command_his_create_time (create_time);
```

执行 DDL 前必须使用 `show index` 确认不存在同等前缀的索引。数据量较大的业务库应评估在线 DDL 耗时和主从复制影响，在低峰执行。

## 6. 任务执行顺序

每次定时任务按以下顺序执行：

1. 检查总开关并获取分布式锁。
2. 计算截止时间。
3. 统计超期 `WaitSend` 和 `Processing` 数量并记录告警。
4. 分批删除 `command_record_his`。
5. 按 `event_key` 分批删除所有超过三个月的 `command_record`。
6. 分批删除 `domain_event_consume_record`。
7. 分批删除 `domain_event_record`。
8. 输出删除统计、异常数据统计和总耗时。
9. 释放分布式锁。

单表某批返回删除数量小于 `batchSize` 时，认为该表本次已清理完成；达到 `maxBatchesPerRun` 后停止该表的本次清理，剩余数据由下一次定时任务继续处理。

## 7. 测试计划

### 7.1 仓储测试

为 `MessageRecordCleanupJdbcRepository` 增加测试，验证：

- 只删除截止时间之前的 `SendSuccess` 和 `SendFailed`。
- 不删除 `WaitSend`。
- 只删除截止时间之前的 `Success` 消费记录。
- 不删除 `Processing`。
- 命令历史按截止时间和批次大小删除。
- 命令组无论成功或失败，只要整组早于截止时间就返回为可清理数据。
- 命令记录按 `event_key` 整组删除，不会保留部分子命令。
- 删除命令主记录前先删除对应的命令历史。
- 查询和删除均不超过配置的批次大小。

### 7.2 服务测试

为 `MessageRecordCleanupService` 增加测试，验证：

- 截止时间为当前北京时间减去配置月数。
- 配置开关关闭的表不调用对应仓储。
- 删除数量达到 `batchSize` 时继续下一批。
- 删除数量小于 `batchSize` 时停止当前表的循环。
- 达到 `maxBatchesPerRun` 后不再继续删除。
- 按命令历史、命令主记录、消费记录、事件记录的顺序执行。
- 某批执行失败时不影响已提交的历史批次。

### 7.3 任务测试

为 `MessageRecordCleanupTask` 增加测试，验证：

- 只有开关开启时创建或执行清理任务。
- 多次触发时通过固定分布式锁互斥。
- 服务返回的删除统计正确写入日志。
- 仓储异常能够输出表名、截止时间和异常堆栈。

### 7.4 回归验证

```bash
./gradlew test --tests '*MessageRecordCleanup*'
./gradlew test
```

需要同时验证：

- 事件发布定时任务仍能正常扫描 `WaitSend` 记录。
- 普通和数据库幂等消费逻辑不受影响。
- 聚合命令失败重试仍能从未完成的子命令继续。

## 8. 数据库上线前检查

### 8.1 历史数据量统计

使用和程序一致的截止时间，执行：

```sql
select status, count(*)
from domain_event_record
where create_time < '<cutoff_time>'
group by status;

select status, count(*)
from domain_event_consume_record
where create_time < '<cutoff_time>'
group by status;

select success, count(*)
from command_record
where create_time < '<cutoff_time>'
group by success;

select count(*)
from command_record_his
where create_time < '<cutoff_time>';
```

### 8.2 异常数据检查

```sql
select count(*)
from domain_event_record
where status = 'WaitSend'
  and create_time < '<cutoff_time>';

select count(*)
from domain_event_consume_record
where status = 'Processing'
  and create_time < '<cutoff_time>';
```

如存在大量超期 `WaitSend` 或 `Processing` 数据，需先排查消息发布或事务配置问题，不应用清理任务掩盖故障。

### 8.3 执行计划确认

针对清理 SQL 执行 `explain`，确认使用预期索引，不存在大表全表扫描。

## 9. 上线与存量清理步骤

### 9.1 第一阶段：代码上线，保持开关关闭

1. 完成 `common-lib` 代码和测试。
2. 发布新版本 `common-lib`。
3. 业务服务升级依赖，保持 `tehang.message.cleanup.enabled=false`。
4. 验证事件发布、消费和命令功能无回归问题。

### 9.2 第二阶段：数据库索引上线

1. 确认现有索引。
2. 为消费表、命令表和命令历史表增加缺失的清理索引。
3. 在低峰执行 DDL，观察主库负载和主从复制延迟。

### 9.3 第三阶段：开启小批量存量清理

首次建议配置：

```yaml
tehang:
  message:
    cleanup:
      enabled: true
      retentionMonths: 3
      batchSize: 500
      maxBatchesPerRun: 10
      cron: "0 30 3 * * ?"
      eventRecordEnabled: true
      consumeRecordEnabled: true
      commandRecordEnabled: true
```

该配置每张表单次最多清理约 5000 条。连续观察 2～3 天，确认：

- 无明显慢 SQL。
- 无长事务和锁等待。
- 主从复制延迟在可接受范围。
- 未发生 `WaitSend` 或 `Processing` 误删，命令记录按 `event_key` 整组删除。

### 9.4 第四阶段：调整为日常配置

存量历史数据基本清理后，调整为：

```yaml
tehang:
  message:
    cleanup:
      enabled: true
      retentionMonths: 3
      batchSize: 1000
      maxBatchesPerRun: 50
      cron: "0 30 3 * * ?"
```

## 10. 监控与运维

每次任务至少输出：

- 清理截止时间。
- 每张表的删除数量。
- 每张表的执行批次数。
- 超期 `WaitSend` 和 `Processing` 记录数量。
- 任务总耗时。
- 执行失败的表名和异常信息。

建议配置告警：

- 清理任务连续 2 天未成功执行。
- 超过三个月的 `WaitSend` 数量大于 0。
- 超过三个月的 `Processing` 数量大于 0。
- 每次任务持续达到 `maxBatchesPerRun`，说明清理速度低于数据增长速度。

## 11. 验收标准

- 清理功能默认关闭，未显式启用的服务无数据删除行为。
- 开启后每日按配置时间执行，多实例环境只有一个实例实际清理。
- 只保留最近三个月的已完成事件、成功消费和已完成命令数据。
- `WaitSend` 和 `Processing` 不被自动删除；超过三个月的命令不判断成功状态。
- 每批删除数量不超过配置的 `batchSize`。
- 单次任务不超过配置的 `maxBatchesPerRun`。
- 清理期间事件发布、消费和命令重试功能正常。
- 任务日志可明确追溯每次清理的截止时间、删除数量和异常原因。

## 12. 回滚策略

### 12.1 代码回滚

1. 将 `tehang.message.cleanup.enabled` 设置为 `false`，可立即停止后续定时清理。
2. 如需要，将业务服务回滚到上一版 `common-lib`。
3. 新增索引可保留，不影响现有消息功能。

### 12.2 数据回滚

删除操作本身不可逆。首次开启前必须确认数据库备份可用，并记录首次清理的截止时间。如发生误删，只能从备份或 binlog 中恢复。

因此，首次生产执行前必须完成：

- 根据相同条件执行 `select count(*)` 确认影响范围。
- 确认备份或 binlog 保留时间覆盖首次清理窗口。
- 使用小批次配置执行。
- 安排人员观察数据库负载和业务消息处理指标。

## 13. 暂不执行的事项

- 不建设历史归档表或冷存储，超过三个月的可清理数据直接删除。
- 不引入分区表。
- 不修改现有事件发布、MQ 消费和命令执行流程。
- 不为超过三个月的消息继续保留发布去重或消费幂等能力。
- 不自动强制关闭超期待发送事件。

## 14. 推荐执行顺序

1. 评审本执行计划和数据保留边界。
2. 实现清理配置、定时任务、服务和 JDBC 仓储。
3. 补充单元测试和回归测试。
4. 发布 `common-lib`，业务服务先保持清理开关关闭。
5. 执行数据统计、异常数检查和 SQL `explain`。
6. 在低峰时段增加缺失索引。
7. 以小批次开启首次生产清理。
8. 观察 2～3 天后调整为日常批次配置。
9. 持续监控超期 `WaitSend`、`Processing` 数据和清理任务执行结果。
