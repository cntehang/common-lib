# 通用事件发布去重与消费幂等两阶段执行计划

## 1. 执行原则

本计划基于《通用事件发布去重与消费幂等方案》，采用两阶段落地：

- 阶段一：先实现 Outbox 发布去重，解决重复发布导致重复写 `domain_event_record`、重复投递 MQ 的问题。
- 阶段二：再实现 Inbox 消费幂等，解决关键订阅者重复消费导致重复业务副作用的问题。

两阶段分开执行，便于独立验证、降低一次性改动范围，也方便在 `tmc-services` 中先确认 `FlightBookingCompletedEvent` 的重复发布问题是否已被收敛。

本计划只描述执行步骤。代码实现需在计划审阅通过后再开始。

## 2. 阶段一：Outbox 发布去重

### 2.1 目标

为 `TransactionalEventPublisher` 增加显式发布去重能力。调用方通过稳定业务 key 调用 `publishOnce`，同一 `event_type + event_key` 只写入一条 `domain_event_record`，避免重复投递 MQ。

### 2.2 `common-lib` 改动范围

1. 扩展 `TransactionalEventPublisher`
   - 新增 `publishOnce(DomainEvent event, String idempotentKey)`。
   - 新增 `publishOnce(DomainEvent event, String idempotentKey, BjTime startDeliverTime)`。
   - 校验 `idempotentKey` 非空，长度不超过 100。
   - 方法内将 `event.key` 设置为 `idempotentKey`。
   - 首次插入返回 `true`，重复插入返回 `false` 并记录 `warn`。
   - 保持现有 `publish`、`publishDirectly` 语义不变。

2. 扩展 `DomainEventRecordJdbcRepository`
   - 新增 `addOnce(DomainEventRecord record)`。
   - 复用现有 insert SQL。
   - 捕获 `DuplicateKeyException` 返回 `false`。
   - 其他异常继续抛出，由发布服务包装为 `SystemErrorException`。

3. 更新启用说明
   - 在 `EnableTransactionalDomainEvent` 的建表说明中补充唯一约束。
   - 更新事件文档中事务性发布说明。

### 2.3 数据库迁移

在使用事务性事件发布的业务库中执行前置检查：

```sql
select event_type, event_key, count(*) as cnt
from domain_event_record
group by event_type, event_key
having count(*) > 1;
```

确认无历史冲突后增加唯一约束：

```sql
alter table domain_event_record
  add unique key uk_domain_event_record_type_key (event_type, event_key);
```

如果存在历史重复数据，先由业务确认重复记录是否可归档或清理，再添加约束。

### 2.4 `tmc-services` 接入范围

1. 将 `FlightBookingCompletedEvent` 的所有发布点改为 `publishOnce`。
2. 使用稳定 key：

```java
"TMC-FlightBookingCompleted:" + orderId
```

3. 暂不改消费者逻辑，避免阶段一扩大影响面。

### 2.5 测试验证

`common-lib` 测试：

- `publishOnce` 首次调用插入成功并返回 `true`。
- 相同 `event_type + event_key` 重复调用返回 `false`。
- 重复调用不会新增 `domain_event_record`。
- 重复调用不会影响普通 `publish`。
- `idempotentKey` 为空或超长时抛出明确异常。

`tmc-services` 测试：

- 多个入口重复发布 `FlightBookingCompletedEvent` 时，只生成一条 `domain_event_record`。
- 已有普通事件发布不受影响。

回归命令：

```bash
./gradlew test --tests '*FlightBookingCompletedEvent*'
./gradlew test
```

### 2.6 验收标准

- `publishOnce` 对重复业务 key 返回 `false`，不再次写 outbox。
- 普通 `publish` 行为与现有版本一致。
- `FlightBookingCompletedEvent` 重复发布问题被收敛。
- 无消费者侧行为变更。

### 2.7 回滚策略

- 代码回滚：业务发布点从 `publishOnce` 恢复为 `publish`。
- 数据库回滚：如需回滚唯一约束，先确认是否已有依赖唯一约束的重复发布保护，再执行 `drop index uk_domain_event_record_type_key on domain_event_record`。

## 3. 阶段二：Inbox 消费幂等

### 3.1 目标

为关键集群订阅者提供显式 Inbox 消费幂等能力。同一 `event_key + event_type + subscriber_id` 只成功处理一次，避免 MQ 重投或并发重复消费导致重复记账、重复生成明细或重复发布后续事件。

### 3.2 `common-lib` 改动范围

1. 新增标记接口

```java
public interface DatabaseIdempotentClusteringEventSubscriber extends ClusteringEventSubscriber {

}
```

2. 扩展 `EventSubscriber`
   - 新增默认方法 `subscriberId()`。
   - 默认返回 `getClass().getName()`。
   - 文档建议关键订阅者显式覆盖稳定业务 id。

3. 新增 Inbox 消费记录模型
   - `DomainEventConsumeRecord`。
   - `DomainEventConsumeStatus`。
   - `DomainEventConsumeRecordJdbcRepository`。
   - `DomainEventConsumeService`。

4. 修改 `ClusteringMqConsumer`
   - 普通 `ClusteringEventSubscriber`：继续走现有 Redis 24 小时防重逻辑。
   - 普通订阅者分布式锁和 Redis 防重 key 粒度改为 `eventType + eventKey`。
   - `DatabaseIdempotentClusteringEventSubscriber`：不走 Redis 防重，不获取分布式锁，直接进入 `DomainEventConsumeService`。
   - `DomainEventConsumeService.consume` 使用事务包裹消费记录插入、订阅者处理、成功状态更新。

5. 更新启用说明
   - `EnableTransactionalDomainEvent` 导入 Inbox 相关组件。
   - 文档说明只有实现 `DatabaseIdempotentClusteringEventSubscriber` 的服务才需要消费记录表。

### 3.3 数据库迁移

仅在存在 `DatabaseIdempotentClusteringEventSubscriber` 的服务数据库中创建：

```sql
create table if not exists `domain_event_consume_record`
(
  `id`             varchar(50)  not null comment 'PK, uuid',
  `event_key`      varchar(100) not null comment '事件key',
  `event_type`     varchar(100) not null comment '事件类型',
  `subscriber_id`  varchar(200) not null comment '订阅者稳定标识',
  `status`         varchar(30)  not null comment '消费状态',
  `consume_time`   varchar(23)  null     comment '消费成功时间',
  `error_message`  varchar(500) null     comment '错误信息，预留字段',
  `create_time`    varchar(23)  not null comment '创建时间',
  `update_time`    varchar(23)  not null comment '更新时间',
  primary key (`id`),
  unique key `uk_event_consume` (`event_key`, `event_type`, `subscriber_id`),
  key `idx_domain_event_consume_record_event` (`event_type`, `event_key`),
  key `idx_domain_event_consume_record_subscriber` (`subscriber_id`)
) engine = innodb default charset = utf8mb4 comment = '领域事件消费记录表';
```

无数据库服务和普通订阅者服务不需要创建该表。

### 3.4 `tmc-services` 接入范围

1. 选择 `FlightBookingCompletedEvent` 对应关键订阅者作为首个接入点。
2. 让该订阅者实现 `DatabaseIdempotentClusteringEventSubscriber`。
3. 显式覆盖稳定 `subscriberId()`，例如：

```java
return "tmc-services.flight-booking-completed";
```

4. 移除只为防重复消费而写在业务表或订阅者内部的重复判断。
5. 检查订阅者内部是否调用外部系统；如存在外部副作用，必须先确认外部幂等或拆分为任务表/后续事件。

### 3.5 测试验证

`common-lib` 测试：

- 普通 `ClusteringEventSubscriber` 不进入 `DomainEventConsumeService`。
- 普通订阅者仍使用 Redis 防重与分布式锁。
- 普通订阅者锁 key 和 Redis 防重 key 使用 `eventType + eventKey`。
- `DatabaseIdempotentClusteringEventSubscriber` 不读写 Redis 防重 key。
- `DatabaseIdempotentClusteringEventSubscriber` 不获取分布式锁。
- 首次消费成功后写入 `Success` 消费记录。
- 重复消费同一 `event_key + event_type + subscriber_id` 不再调用 `handleEvent`。
- `handleEvent` 抛异常时事务回滚，不写 `Success` 记录。
- 失败后再次消费会重新调用 `handleEvent`。

`tmc-services` 测试：

- 重复消费 `FlightBookingCompletedEvent` 不重复记账。
- 重复消费不重复生成消费明细。
- 重复消费不重复发布 `FlightOrderChangedEvent`。
- 首次消费失败后，MQ 重试能再次执行业务处理。

回归命令：

```bash
./gradlew test --tests '*FlightBookingCompletedEvent*'
./gradlew test
```

### 3.6 验收标准

- 普通订阅者行为保持兼容。
- 无数据库服务升级后不需要 datasource 或消费记录表。
- 数据库幂等订阅者重复消费不会重复执行业务逻辑。
- 数据库幂等订阅者失败后不会误写成功记录，MQ 可继续重试。
- `subscriber_id` 稳定、可读，并在文档中作为持久化协议说明。

### 3.7 回滚策略

- 业务接入回滚：订阅者移除 `DatabaseIdempotentClusteringEventSubscriber`，恢复普通消费路径。
- 数据库表可保留，不影响普通消费。
- 如 common-lib 需要回滚，先确认业务服务不再实现 `DatabaseIdempotentClusteringEventSubscriber`。

## 4. 推荐执行顺序

1. 审阅本执行计划。
2. 执行阶段一：实现 `publishOnce`、添加 outbox 唯一约束、接入 `FlightBookingCompletedEvent` 发布点。
3. 观察阶段一效果，确认重复发布已收敛。
4. 执行阶段二：实现 Inbox 消费幂等、接入关键订阅者。
5. 观察关键订阅者重复消费、异常重试、业务副作用是否符合预期。

## 5. 暂不执行的事项

- 不对所有订阅者默认启用数据库幂等。
- 不增加配置开关。
- 不为 `publishDirectly` 增加去重版本。
- 不把广播消费者纳入本轮 Inbox 幂等。
- 不在消费事务中新增外部系统调用补偿机制；外部副作用幂等由业务接入方单独评估。
