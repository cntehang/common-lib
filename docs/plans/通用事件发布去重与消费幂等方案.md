# 通用事件发布去重与消费幂等方案

## 1. 背景

`common-lib` 当前事件组件已经具备事务性 outbox 发布能力：

- `TransactionalEventPublisher` 将事件写入 `domain_event_record`。
- `SendDomainEventRecordsToMqService` 定时扫描待发送记录并投递 MQ。
- `ClusteringMqConsumer` 负责集群消费，并使用 Redis key 做 24 小时快速防重。

现有 Redis 幂等只能覆盖短时间重复投递，无法作为最终一致的消费依据；发布侧也缺少基于稳定业务 key 的去重能力。为支持 `tmc-services` 中类似 `FlightBookingCompletedEvent` 的业务场景，需要在 `common-lib` 中提供通用的发布去重与消费幂等能力。

本方案定位为 `common-lib` 提供的可选 Outbox/Inbox 幂等基础设施：

- 发布端：Outbox 发布去重。显式调用 `publishOnce` 的事件，使用稳定业务 key 避免重复写入 `domain_event_record`。
- 消费端：Inbox 消费幂等。需要强幂等保护的订阅者显式接入数据库消费记录，保证同一事件、同一订阅者只成功处理一次。
- 普通事件：继续使用现有 `publish`，语义保持不变。
- 普通订阅者：继续使用现有消费逻辑和 Redis 24 小时快速防重，不强制引入数据库事务。
- 业务接入：`FlightBookingCompletedEvent` 等事件只接入通用能力，不再在业务表上额外增加重复消费状态字段。

## 2. 设计原则

1. 只对显式 opt-in 的事件做发布去重，避免改变现有事件语义。
2. Inbox 消费幂等是订阅者级别的显式接入能力，不对所有 `ClusteringEventSubscriber` 强制开启。
3. 已接入数据库消费幂等的订阅者，只使用数据库消费记录做幂等判断，不再叠加 Redis 防重判断。
4. 已接入数据库消费幂等的订阅者，业务处理与消费成功记录必须在同一个事务中提交或回滚。
5. 数据库幂等订阅者消费失败时不落成功记录，让 MQ 后续重试仍能再次执行。
6. 事件 key 和订阅者 id 必须稳定，不能使用内存地址、随机值或部署实例相关值。
7. 不承诺严格 exactly-once；涉及外部系统调用时，订阅者仍需按业务风险单独保证外部幂等。

## 3. 发布端方案：Outbox 去重

### 3.1 API 扩展

在 `TransactionalEventPublisher` 中新增：

```java
public boolean publishOnce(DomainEvent event, String idempotentKey)
```

建议同时补充延迟投递重载，保持与现有 `publish` 能力对齐：

```java
public boolean publishOnce(DomainEvent event, String idempotentKey, BjTime startDeliverTime)
```

语义：

- `idempotentKey` 是调用方传入的稳定业务 key。
- `idempotentKey` 必须非空，长度不能超过 `domain_event_record.event_key` 当前定义的 100 字符。
- 方法内部将 `event.key` 设置为 `idempotentKey`。
- 首次插入 `domain_event_record` 返回 `true`。
- 唯一约束冲突时返回 `false`，记录 `warn`，不抛业务异常，不再次投递 MQ。
- 其他数据库异常仍按现有逻辑包装为 `SystemErrorException`。

示例：

```java
transactionalEventPublisher.publishOnce(
    new FlightBookingCompletedEvent(orderId),
    "TMC-FlightBookingCompleted:" + orderId
);
```

### 3.2 Outbox 唯一约束

`domain_event_record` 增加唯一约束：

```sql
alter table domain_event_record
  add unique key uk_domain_event_record_type_key (event_type, event_key);
```

选择 `(event_type, event_key)` 而不是单独 `event_key` 的原因：

- 避免不同事件类型误用相同业务 id 时互相阻塞。
- 与业务语义更贴近：同一事件类型下，同一幂等 key 只发布一次。
- 当前普通事件默认使用 UUID key，增加该唯一约束后通常不受影响。
- 如果历史代码手工设置固定 `event.key` 后继续调用普通 `publish`，重复插入会按唯一约束失败；这类代码应改用 `publishOnce` 或明确调整 key 语义。

上线前需要检查历史数据是否存在重复：

```sql
select event_type, event_key, count(*) as cnt
from domain_event_record
group by event_type, event_key
having count(*) > 1;
```

如存在重复记录，需要先确认是否为历史重复发布，再决定清理、归档或暂缓添加唯一约束。

### 3.3 Repository 行为

`DomainEventRecordJdbcRepository` 建议新增方法：

```java
public boolean addOnce(DomainEventRecord record)
```

实现要点：

- 使用现有 insert SQL。
- 捕获 `DuplicateKeyException` 后返回 `false`。
- 不建议依赖“先查再插”，因为并发下仍需唯一约束兜底。
- `TransactionalEventPublisher.publish` 仍调用原 `add`，保留失败即异常的语义。
- `publishOnce` 调用 `addOnce`，冲突时只记录幂等跳过日志。

### 3.4 不支持 `publishDirectlyOnce`

`publishDirectly` 不经过 outbox 表，无法利用数据库唯一约束保证跨进程、跨重试去重。本方案暂不新增 `publishDirectlyOnce`。如果业务要求直接发布且去重，应由业务方自行持久化去重状态，或改用事务性 outbox 发布。

## 4. 消费端方案：Inbox 幂等

### 4.1 接入边界

消费端数据库幂等不作为所有消费者的默认行为，而是由订阅者显式选择。

推荐新增标记接口：

```java
public interface DatabaseIdempotentClusteringEventSubscriber extends ClusteringEventSubscriber {

}
```

`ClusteringMqConsumer` 根据订阅者类型选择处理路径：

- 普通 `ClusteringEventSubscriber`：保持现有逻辑，继续使用 Redis 24 小时快速防重，不额外开启数据库事务。
- `DatabaseIdempotentClusteringEventSubscriber`：使用 `domain_event_consume_record` 做最终幂等依据，并将订阅者处理逻辑与消费成功记录放到同一个事务中。

这样可以避免两个问题：

- 轻量事件、缓存刷新、通知类订阅者不承担额外数据库写入与事务成本。
- 只使用 `@EnableDomainEvent`、本身没有数据库的服务，不会因为升级 `common-lib` 被强制依赖 datasource 或消费记录表。

注意：实现 `DatabaseIdempotentClusteringEventSubscriber` 的服务必须具备数据库能力，并完成 `domain_event_consume_record` 建表。若订阅者显式要求数据库幂等但运行环境没有导入对应消费幂等组件，应启动失败或消费失败并告警，不能静默降级为普通消费，否则会破坏订阅者声明的幂等语义。

### 4.2 新增消费记录表

接入 `DatabaseIdempotentClusteringEventSubscriber` 的服务需要新增 `domain_event_consume_record`：

```sql
create table if not exists `domain_event_consume_record`
(
  `id`             varchar(50)  not null comment 'PK, uuid',
  `event_key`      varchar(100) not null comment '事件key',
  `event_type`     varchar(100) not null comment '事件类型',
  `subscriber_id`  varchar(200) not null comment '订阅者稳定标识',
  `status`         varchar(30)  not null comment '消费状态',
  `consume_time`   varchar(23)  null     comment '消费成功时间',
  `error_message`  varchar(500) null     comment '错误信息，预留字段',
  `create_time`    varchar(23)  not null comment '创建时间',
  `update_time`    varchar(23)  not null comment '更新时间',
  primary key (`id`),
  unique key `uk_event_consume` (`event_key`, `event_type`, `subscriber_id`),
  key `idx_domain_event_consume_record_event` (`event_type`, `event_key`),
  key `idx_domain_event_consume_record_subscriber` (`subscriber_id`)
) engine = innodb default charset = utf8mb4 comment = '领域事件消费记录表';
```

`status` 建议定义枚举：

- `Processing`：事务内占位状态，用于让数据库唯一约束在并发重复消费时生效；正常提交前会更新为 `Success`，失败时随事务回滚，不应长期保留。
- `Success`：订阅者处理成功，重复消息可直接跳过。

失败时事务回滚，不提交 `Processing` 或 `Success` 记录。因此表内正常可见记录应主要是 `Success`；`Processing` 不作为可恢复任务状态使用。`error_message` 作为后续扩展字段预留，本阶段主要依赖日志与 MQ 重试。

### 4.3 稳定订阅者 id

当前 `EventSubscriber.getInstanceId()` 返回 `类名 + 内存地址 hash`，只适合日志，不适合持久化幂等记录。

建议在 `EventSubscriber` 增加默认方法：

```java
default String subscriberId() {
  return getClass().getName();
}
```

业务长期稳定的订阅者建议显式覆盖：

```java
@Override
public String subscriberId() {
  return "tmc-services.flight-booking-completed";
}
```

注意：

- `subscriber_id` 一旦上线，应视为持久化协议的一部分。
- 重命名类、迁移包路径或拆分订阅者时，需要评估是否保留旧 id。
- 不能使用 `getInstanceId()`、机器名、pod 名称或随机 UUID。

### 4.4 消费服务

新增独立服务承载事务边界，例如：

```java
@Service
@AllArgsConstructor
public class DomainEventConsumeService {

  private final DomainEventConsumeRecordJdbcRepository consumeRecordJdbcRepository;

  @Transactional
  public boolean consume(DatabaseIdempotentClusteringEventSubscriber subscriber, DomainEvent event) {
    String subscriberId = subscriber.subscriberId();
    boolean inserted = consumeRecordJdbcRepository.insertProcessing(event, subscriberId);
    if (!inserted) {
      return false;
    }

    subscriber.handleEvent(event);
    consumeRecordJdbcRepository.updateSuccess(event, subscriberId);
    return true;
  }
}
```

实现要点：

- `ClusteringMqConsumer` 不直接声明事务，避免消费者类职责继续膨胀。
- `ClusteringMqConsumer` 仅在订阅者实现 `DatabaseIdempotentClusteringEventSubscriber` 时调用该服务；普通订阅者继续走原 `handleEventForSubscriber` 逻辑。
- `DomainEventConsumeService.consume` 使用 `@Transactional`，由 Spring 代理生效。
- `insertProcessing` 依赖 `uk_event_consume` 做并发防重。
- 捕获 `DuplicateKeyException` 时表示已有成功消费或并发消费已经提交成功，返回 `false` 并记录 `warn`。
- 如果 `subscriber.handleEvent(event)` 抛异常，事务回滚，消费记录不落库，外层返回 `Action.ReconsumeLater`。
- 如果业务处理成功但 `updateSuccess` 失败，事务整体回滚，MQ 重试会再次调用订阅者。因此订阅者内部调用外部系统时仍需要额外幂等。
- 对没有数据库幂等要求的普通订阅者，不应进入该事务服务，以免扩大事务范围和增加数据库压力。

### 4.5 Redis 防重边界

现有 Redis 24 小时防重逻辑只保留给普通订阅者。数据库幂等订阅者不再使用 Redis 作为防重判断，也不在消费成功后额外写 Redis `OK`。

这样设计的原因：

1. Redis 命中后如果仍需查询数据库，性能收益有限，反而增加逻辑复杂度。
2. Redis 命中后如果直接跳过，可能在事务回滚、缓存残留或误写时跳过本该重试的消息。
3. 数据库唯一约束已经能处理重复消费，额外 Redis 状态会增加排查成本。

对普通订阅者，保持现有 Redis 24 小时防重逻辑，不新增数据库查询。

### 4.6 与现有分布式锁的关系

分布式锁只保留给普通订阅者，用于配合 Redis 24 小时防重，避免并发重复消息同时读到 Redis 为空并重复执行 `handleEvent`。

普通订阅者锁粒度建议调整为：

```text
MQ_Consumer_Lock_${eventType}_${eventKey}
```

这样可以避免不同事件类型刚好复用相同 `event.key` 时互相阻塞。

如果后续支持同一 `eventType` 多个集群订阅者，锁粒度再扩展为：

```text
MQ_Consumer_Lock_${eventType}_${eventKey}_${subscriberId}
```

数据库幂等订阅者不使用分布式锁，只依赖 `domain_event_consume_record` 唯一约束与事务保证并发重复消费不会重复执行业务逻辑。

## 5. 消费流程

普通订阅者消费流程：

```text
MQ message
  -> ClusteringMqConsumer 反序列化 DomainEvent
  -> 获取分布式锁，锁粒度为 eventType + eventKey
  -> 使用现有 Redis 24 小时防重逻辑
       -> Redis 无 OK：subscriber.handleEvent(event)，成功后写 Redis OK
       -> Redis 有 OK：认为短期内已处理，跳过
  -> CommitMessage
```

数据库幂等订阅者重复消息处理流程：

```text
MQ message
  -> ClusteringMqConsumer 反序列化 DomainEvent
  -> DomainEventConsumeService.consume(...)
       -> insert Processing consume record
          -> 唯一键冲突：已有成功消费或并发消费已占位，返回 false
       -> subscriber.handleEvent(event)
       -> update status = Success, consume_time = now
       -> 事务提交
  -> CommitMessage
```

数据库幂等订阅者异常流程：

```text
MQ message
  -> insert Processing consume record
  -> subscriber.handleEvent(event) 抛异常
  -> 事务回滚，消费记录不提交
  -> ClusteringMqConsumer 返回 ReconsumeLater
  -> MQ 后续重试
```

## 6. `FlightBookingCompletedEvent` 接入建议

在 `tmc-services` 中，所有 `FlightBookingCompletedEvent` 发布点改为：

```java
transactionalEventPublisher.publishOnce(
    new FlightBookingCompletedEvent(orderId),
    "TMC-FlightBookingCompleted:" + orderId
);
```

订阅者处理建议：

- `FlightBookingCompletedEvent` 对应订阅者实现 `DatabaseIdempotentClusteringEventSubscriber`，显式接入数据库消费幂等。
- 移除只为防重复消费而增加的本地判断或订单状态字段。
- 依赖 `domain_event_consume_record` 保证同一事件、同一订阅者成功处理一次。
- 如果订阅者内部会调用外部系统、生成不可回滚流水或发送二次 MQ，需要继续检查这些副作用自身的幂等能力。
- 如果订阅者会发布后续事件，例如 `FlightOrderChangedEvent`，该发布动作应位于同一个业务事务中，或按业务要求额外使用 `publishOnce`。

## 7. 兼容性与迁移步骤

### 7.1 `common-lib` 改造

1. 新增 `TransactionalEventPublisher.publishOnce` API。
2. 新增 `DomainEventRecordJdbcRepository.addOnce`。
3. 新增 `DatabaseIdempotentClusteringEventSubscriber`，作为数据库消费幂等的显式接入标记。
4. 新增 `DomainEventConsumeRecord`、`DomainEventConsumeStatus`、`DomainEventConsumeRecordJdbcRepository`。
5. 新增 `DomainEventConsumeService`，承载消费事务。
6. 修改 `ClusteringMqConsumer`：普通订阅者走现有 Redis 防重逻辑；数据库幂等订阅者走 `DomainEventConsumeService`。
7. 在 `EventSubscriber` 增加 `subscriberId()` 默认方法。
8. 更新 `EnableTransactionalDomainEvent` 的导入列表和建表说明。

### 7.2 数据库迁移

在需要发布去重或接入数据库消费幂等的服务数据库执行：

1. 检查 `domain_event_record` 历史重复数据。
2. 为 `domain_event_record` 增加 `uk_domain_event_record_type_key`。
3. 如果服务内存在 `DatabaseIdempotentClusteringEventSubscriber`，创建 `domain_event_consume_record`。
4. 发布 `common-lib` 新版本。
5. 业务服务升级依赖，完成发布点替换，并让关键订阅者显式实现 `DatabaseIdempotentClusteringEventSubscriber`。

只使用 `@EnableDomainEvent` 且没有数据库的服务，不需要创建消费记录表；普通订阅者也不需要修改。

### 7.3 灰度策略

建议先在非核心事件或测试环境验证：

- 重复调用 `publishOnce` 是否只生成一条 outbox 记录。
- 普通订阅者是否仍按现有 Redis 防重逻辑正常消费。
- 数据库幂等订阅者在 MQ 手工重投同一消息时是否只执行一次订阅者逻辑。
- 数据库幂等订阅者抛异常后是否没有消费成功记录，且 MQ 能重试。
- 无数据库服务升级 `common-lib` 后是否不需要额外 datasource 或建表。

确认后再切换 `FlightBookingCompletedEvent` 所有发布入口。

## 8. 测试计划

### 8.1 `common-lib` 单元测试

- `publishOnce` 首次调用插入成功并返回 `true`。
- `publishOnce` 使用相同 `event_type + event_key` 重复调用返回 `false`，不新增 outbox 记录。
- 重复 key 冲突时记录 `warn`，不抛 `SystemErrorException`。
- 普通 `publish` 行为不变。
- 普通 `ClusteringEventSubscriber` 不进入 `DomainEventConsumeService`，继续走现有 Redis 防重逻辑。
- `DatabaseIdempotentClusteringEventSubscriber` 消费成功后再次消费同一 `event_key + event_type + subscriber_id`，不再调用 `subscriber.handleEvent`。
- `DatabaseIdempotentClusteringEventSubscriber` 消费异常时事务回滚，不写 `Success` 记录，再次消费会重新调用订阅者。
- `DatabaseIdempotentClusteringEventSubscriber` 不读写 Redis 防重 key，只依赖 `domain_event_consume_record`。
- 未导入数据库消费幂等组件时，普通订阅者仍可正常启动和消费。

### 8.2 `tmc-services` 测试

- 多个入口重复发布 `FlightBookingCompletedEvent` 时，只生成一条 `domain_event_record`。
- 重复消费同一 `FlightBookingCompletedEvent` 时，不重复记账、不重复生成消费明细、不重复发布 `FlightOrderChangedEvent`。
- 首次消费失败后，重试能再次执行业务处理。

### 8.3 回归命令

```bash
./gradlew test --tests '*FlightBookingCompletedEvent*'
./gradlew test
```

## 9. 风险与注意事项

- 添加唯一约束前必须检查历史 outbox 数据，否则迁移可能失败。
- `subscriber_id` 是持久化幂等协议，不能随意变更。
- 数据库消费幂等会增加数据库写入和事务成本，只适合关键业务订阅者显式接入，不应作为所有订阅者默认行为。
- 无数据库服务不能实现 `DatabaseIdempotentClusteringEventSubscriber`；如果误实现，应尽早失败并告警。
- `publishOnce` 的 key 必须由业务稳定字段组成，不应包含当前时间、随机数或请求流水号。
- 对同一业务动作可能有多个事件类型时，建议 key 前缀包含事件类型或业务动作，例如 `TMC-FlightBookingCompleted:${orderId}`。
- 本方案保证“同一事件同一订阅者成功处理只提交一次”，不保证外部系统副作用 exactly-once。
- 如果订阅者事务中包含耗时外部调用，会扩大事务范围；应优先把外部调用设计为幂等，或拆分为后续事件/任务。
- 广播消费者当前不纳入本方案。广播模式的语义是每个实例都消费一次，不适合直接套用集群消费的订阅者级幂等。

## 10. 决策结论

推荐在 `common-lib` 中实现通用 `publishOnce` 与订阅者显式接入的数据库消费记录幂等能力。`FlightBookingCompletedEvent` 只作为首个业务接入方，通过稳定 key 接入发布去重，并让关键订阅者实现 `DatabaseIdempotentClusteringEventSubscriber`；业务订阅者不再维护专用重复消费字段。

该方案能覆盖重复发布和关键订阅者 MQ 重投后的重复消费问题；同时普通订阅者和无数据库服务继续保持现有轻量消费方式，不引入额外配置开关。
